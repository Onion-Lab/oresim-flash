# tests — 웹판 검증

계산 엔진(`public/js/engine.js`)이 원래 Flash판(AS3)과 **동작이 같은지**, 표(`public/js/const.js`)가 원본(`data/tables.json`)과 같은지,
화면(`public/`)이 엔진 상태를 바르게 보여 주고 사람의 입력을 바르게 보내는지 확인하는 스크립트들이다. 저장소 맨 위에서 실행한다.
엔진 시험은 Node 22 만 있으면 된다(설치할 것 없음). 화면 시험 둘(`web-smoke.js`, `web-diff.js`)은 Playwright 가 있을 때만 돌고,
없으면 그렇게 말하고 종료 코드 0 으로 끝난다(아래 '화면 시험').

2026-11-04 에 Flash판과 원본 하네스(AS3 를 Node 에서 헤드리스로 돌리던 `harness.js`)를 저장소에서 지웠다. 그 전까지 엔진은 원본과 조작마다 비교했고
(`engine-diff.js`), 지우기 직전 그 비교를 지나간 엔진의 결과를 정답 기록 `golden/engine.json` 으로 남겼다. 그 뒤로는 엔진이 기준이다.
원본을 다시 돌려야 하면 git 기록(커밋 `0261cbe`)의 `tests/harness.js`, `tests/engine-diff.js`, `oresim/` 을 꺼내 쓴다.

최고 레벨과 스탯 상한은 스크립트마다 표(`MAX_LEVEL`, `MAX_STATUS`)에서 읽는다(지금 둘 다 255). 상한 둘레의 값(MAX−1, MAX, MAX+1), 무작위 값의 범위(1~MAX),
정해 둔 순서의 이름에 든 숫자('LV 255 까지', '스탯 상한 255')도 그것으로 만들므로, 상한만 바꿀 때는 시험을 고치지 않는다(정답 기록만 다시 만든다).
일부러 범위 밖으로 넣는 값(300, 999, 160000 등)은 상한이 255 여도 범위 밖이다.
상한이 285이던 판의 계획처럼 상한을 넘는 값(상한 + 1, 상한 + 15, 상한 + 30 등)도 표의 상한에서 셈한다.

## 정답 기록 시험(`engine-golden.js`)

조작마다 결과값, 상태 전체(`_debugState()`: 컨트롤 글자 전부, 버튼 표시, 콤보박스, 드롭다운 색, 보너스 스테퍼, `_xi`·`_needXien`·`_bonusPoints`·`logindex` 등
전역, `log` 배열 전체(센티널과 그 뒤 옛 항목까지), `stLog`, `tmpStLog`, 로그 상자 글), `view()`, `exportLog()`, `guide()` 를 빠짐없이 글로 바꿔(NaN·-0·
Infinity·undefined·배열의 빈 칸까지 구별한다) 단위마다 SHA-1 로 이어 붙인다. 단위는 정해 둔 순서 하나, 경계 입력 하나(캐릭터 0·9·15 로 시작하는 엔진마다),
답을 아는 경우 하나, 큰 입력 하나, seed 하나다. seed 는 조작 50개마다 중간 지문을 남겨 어긋나면 어느 50조작 안인지 알린다.
`stLog`/`tmpStLog` 는 값이 있는 칸만 본다(원본의 되돌리기는 0 ~ LV+1 칸에 `undefined` 를 채우는데 엔진은 값이 있는 칸만 옮긴다. 원본 논리는 빈 칸과
`undefined` 칸, 배열 길이를 구별하지 않는다).

기록(2026-11-04): 단위 246개와 seed 308개(1~300 × 400조작, 1001~1008 × 1500조작)를 원본 하네스와 함께 돌려, 조작마다 결과·상태 전체·`view()`(와 원본 상태에서
따로 계산한 화면 값)·`exportLog()`·`guide()` 를 원본과 비교하고 `preview()`/`previewDash(i)` 를 원본이 실제로 한 레벨업·대시와 비교해 어긋남 0 인 채로 썼다
(비교한 상태 307,930개, 18분 27초). 그 뒤 원본 없이 다시 돌린 `--all` 이 기록과 같았다.

기록과 따로, 조작마다 엔진 안에서도 맞춰 본다(원본이 없어도 된다).
- `view()` = 내부 상태(`stateS`)에서 따로 계산한 화면 값(`oracleView`)
- `preview()`/`previewDash(i)` = 그 뒤 엔진이 실제로 한 레벨업·대시
- 답을 아는 경우: 읽은 글의 결과 = 같은 결과가 나와야 하는 글을 새 엔진에 읽힌 결과(또는 정해 둔 값)

엔진 동작을 일부러 바꿨으면 기록과 다르다며 실패한다. 무엇이 왜 바뀌었는지 확인한 뒤 `node tests/engine-golden.js --update` 로 다시 기록한다(모든 seed 를
돈다). 다시 만든 기록은 원본과 비교한 것이 아니다(기록 머리의 `recorded` 가 그렇게 바뀐다). 표(`data/tables.json`)나 `ENGINE_VERSION` 이 바뀌어도
기록과 다르다고 알린다(기록이 그 판의 표 지문과 엔진 판에 묶여 있다).

### 지나가는 경우

마지막에 "지나간 경우" 표로 횟수를 찍는다. 레벨업(최고 레벨에서 거부 포함), 스탯 +1(상한·포인트 부족 거부 포함),
대시(상한 거부, 최고 레벨에서 포인트가 모자라 아무것도 못 하는 대시 포함), ←/→ 와 Shift+←/→, 보너스%(0, 100, 7·103 처럼
반올림·클램프가 필요한 값, 숫자가 아닌 값), 주력 계열(고를 수 있는 것과 없는 것), 캐릭터·타입 변경(로아미니 포함),
스탯 초기화, 스탯 편집(제자리, 더 높은 LV, LV1, 이상한 값·범위 밖 값), `exportLog → importLog` 왕복(같은 엔진, 다른 캐릭터를
고른 새 엔진), 손으로 고친 로그·망가진 로그·푸터 없는 로그·46칸 `Status`·일본어판 로그(`fixtures/ja-era-logs.js`)·빈 로그,
상한이 285이던 판처럼 LV·스탯이 상한을 넘는 `Status` 줄(`statusLv` 글의 35%는 LV·스탯이 상한을 30까지 넘을 수 있다)과 `LV:` 요약 줄
(손으로 고친 로그 `hand` 는 요약 줄의 LV 나 스탯 하나를 상한 − 1 ~ 상한 + 30 으로 바꾸기도 한다),
AS3 와 JS 가 공백으로 보는지가 갈리는 글자(U+00A0, U+FEFF, U+200B, U+3000, \v 등)를 수 앞·Xien 이름 앞뒤에 넣은 로그,
언제든 `guide()`, `serialize()` 로 엔진을 바꿔 끼우고 계속하기. `importLog` 의 `capped` 가 참인 불러오기와 거짓인 불러오기가 둘 다 나오는지도
센다(`import.capped.*`, `corpus.capped.*`. 내보낸 로그를 다시 읽는 왕복은 상한 안의 값만 쓰므로 `roundtrip.capped.false` 만 나온다).
기록을 만든 실행(`--all`)에서는 최고 레벨 255 에 5,795번, 스탯 상한에 44,493번 닿았고, `capped` 가 참인 불러오기가 무작위 407번, 경계 입력 63번이었다.

무작위 조작 전에 네 가지를 먼저 돌린다(무작위로는 드물게만 닿는 길을 매번 확인한다).
- 정해 둔 조작 순서 11개: 드롭다운을 연 뒤 계열이 적은 캐릭터로 바꾸고 고를 수 없는 Xien 줄을 읽기(`tmpx` 를 마지막 항목으로 줄임),
  같은 캐릭터·타입 다시 고르기, 읽기 중 보너스 33%, 스탯 편집 지점으로 되돌리기, 최고 레벨 대시, 스탯 상한, POINT 9999 넘김 등.
- 손으로 고른 경계 입력 64개(× 캐릭터 셋): 전각 문장부호, 음수 보너스, 공백 없는 `Bonus :75%`(원본도 예외), Xien 뒤 전각 공백·NBSP, Xien 메모,
  `Status` 의 LV 0·음수·300, 46칸 `Status`, 상한이 285이던 판의 로그(상한을 넘는 `Status` 줄, 최고 레벨을 넘는 LV 범위·몰빵, 상한 그대로·상한 + 1,
  수가 아닌 값·음수·아주 큰 수, HP/MP/SP·POINT 만 상한을 넘는 줄, 예외 앞뒤의 상한을 넘는 줄), `LV:` 요약 줄의 여러 모양(요약 줄만 상한을 넘는 옛 몰빵
  로그와 옛 편집 로그, 상한 그대로, LV 만 상한 + 1, 이름이 빠짐·순서가 다름·소문자·`LV :` 머리·수가 아닌 값, 덧붙인 말과 전각 콜론, 예외 뒤,
  마지막 줄이 아닌 요약 줄) 등을 새 엔진에 읽히고 몇 가지 조작을 이어 한다.
- 답을 아는 AS3 의미 35개(`knownAnswers`): "같은 결과가 나와야 하는 글"을 읽은 결과와 같아야 한다.
  예를 들어 `Xien : 검계 STAB/DEX` 뒤의 U+3000 은 떼어지고(그 계열을 고른다) U+2028 은 떼어지지 않는다(그 줄은 무시된다).
  `LV &nbsp;15` 의 U+00A0 는 `parseInt` 가 건너뛰지 않아 그 줄이 무시되고, U+200B 는 건너뛴다. 상한을 넘는 `Status` 줄은 상한 값을 적은
  글과 같은 계획이 되고, 최고 레벨을 넘는 LV 범위(`LV 251 - 285 : AGI`)는 최고 레벨까지의 범위에 최고 레벨의 `AGI * 30` 줄을 더한 글과 같은 계획이
  된다(값은 표의 상한에서 만든다). `LV:` 요약 줄은 읽지 않으므로 값이 상한을 넘는 요약 줄이 있는 글은 그 줄이 없는 글과 같은 계획이 된다.
  원본과 엔진이 같은 실수를 하면 차등 비교로는 보이지 않았으므로 이 답으로 못박는다.
- 큰 입력 8개(`heavyCases`): 원본(하네스)이 몇 초 걸려 끝내던 붙여 넣기(`LV 2 - 160000 : STAB`, `STAB * 2000` 을 LV 2 부터 최고 레벨까지,
  최고 레벨 − 1 줄 × `STAB * 600, DEX * 600`, `STAB * 300001`, 30만 레벨 몰빵 뒤 줄 등). 엔진의 반복 건너뛰기(아래)가 끝 상태를 바꾸지 않는지 본다.

이 시험이 실제로 어긋남을 잡는지는 엔진을 일부러 고장 낸 사본(`ORESIM_ENGINE`)으로 확인한다. 원본과 비교하던 때(`engine-diff`)에 센티널 길이, logOut 호출 위치,
스테퍼 커밋 시점, 콤보박스 범위 줄이기, `\s`, `parseInt` 의 공백, openDrop, 반복 건너뛰기 조건, 저장 형식, 상한 읽기 9가지, `capped` 의 요약 줄 규칙 6가지를
고장 낸 엔진을 모두 잡았다. 기록과 비교하는 지금은 되돌리기(`dashBack`)의 비용 구간 비교, 스테퍼 반올림, 대시의 비용 단계 셈을 하나씩 고장 낸 엔진 3가지를 기본 실행
(`node tests/engine-golden.js`)이 모두 잡았다(기록과 다름 27·59·14건, 2026-11-04).

## `engine-invariants.js` 의 상한 확인

상한이 285이던 판의 로그를 따로 확인한다(`special` 의 `capped.*`).
- `capped.edit78`, `capped.edit46`: 옛 스탯 편집 로그(`Status` LV 최고 레벨 + 15, STAB 상한 + 25, DEX 상한 + 15, 78칸·46칸)를 상한으로 읽어 정해 둔 값
  (LV·시작 LV 255, 스탯, 최고 레벨에서 찍은 AGI 두 번의 필요 포인트만큼 준 POINT, 다시 내보낸 `Status` 칸)이 되고, 다시 내보낸 로그는 `capped` 없이
  같은 계획·같은 글인지
- `capped.levelRange`: 최고 레벨을 넘는 LV 범위(`LV 2 - 285 : STAB`)가 최고 레벨에서 멈추고, `LV 2 - 255 : STAB` 에 `LV 255 : STAB * 30` 을 더한 글과
  같은 계획인지
- `capped.atCap`: 상한 그대로는 `capped` 가 아니고 값도 그대로이며, 한 칸(LV 또는 스탯 하나)만 상한 + 1 이면 `capped` 이고 그 칸만 상한으로 읽는지
- `capped.otherFields`: HP/MP/SP 와 그 범위, POINT 는 상한을 넘어도 그대로 읽고(`capped` 도 아니다) 기록 `log[0]` 에 그대로 남는지
- `capped.afterError`: 읽기가 예외로 멈춰 뒤의 줄을 읽지 않아도 상한을 넘는 줄이 있으면 `capped` 가 참인지
- `capped.nanNegative`: 수가 아닌 값과 음수는 `capped` 가 아니고 바뀌지 않는지(원본과 같은 읽기인지는 `engine-golden` 의 경계 입력이 본다)
- `capped.summaryLine`: LV 는 상한을 넘지 않았는데 스탯이 상한을 넘은 옛 몰빵 로그(상한을 넘는 값이 끝의 `LV:` 요약 줄에만 있다)가 `capped` 이고,
  요약 줄은 계획을 바꾸지 않으며(그 줄이 없는 글과 같은 계획·같은 로그 글), 다시 내보낸 로그는 `capped` 가 아닌지. 요약 줄의 여러 모양(상한 그대로,
  LV 만 상한 + 1, 스탯마다 상한 + 1, 끝에 덧붙인 말, 전각 콜론, 이름이 빠지거나 다르거나 순서가 바뀐 줄, `LV :` 머리, 수가 아닌 값·음수)에서
  `capped` 가 정해 둔 답과 같은지. 상한을 넘는 요약 줄이 마지막 줄이 아니어도(뒤에 빈 줄이나 덧붙인 말이 있는 글, 캐릭터/타입 줄 앞이나 글 맨 앞에 둔 글)
  `capped` 이고 계획은 그대로인지
- `budget.undoHugeLv`: 아주 큰 `Status` LV(99999999)를 상한으로 읽는지 보고, 그런 상태는 이제 로그로 만들 수 없으므로 지금 엔진의
  `serialize()` 를 손으로 고쳐(LV 글자, 기록의 LV 칸, 레벨마다의 `stLog`/`tmpStLog` 키를 밀어) LV 99999999 에 조작 셋이 있는 저장 상태를 되살린 뒤,
  되돌리기·다시 실행(Shift 포함) 네 번이 모두 받아들여져 1초 안에 끝나고 처음 계획으로 돌아오는지 본다(되돌리기가 레벨 수만큼 돌면 작업 한도에서 멈춘다).
- 무작위 왕복의 FLAGS 는 내보낸 로그와 끝 두 줄을 뺀 로그가 `capped` 가 아닌지 본다.

`DIFF_VERBOSE=1` 을 주면 `engine-golden` 이 조작을 하나씩 찍는다. `ORESIM_ENGINE=경로` 를 주면 엔진 시험이 그 엔진 파일로 돈다
(일부러 고장 낸 엔진을 시험이 잡아내는지 볼 때 쓴다).

## 화면 시험(Playwright)

Playwright 는 저장소의 의존성이 아니다(`package.json` 에 의존성이 없다). `require('playwright')` 가 되는 Node 에서 돌리면 된다.
브라우저는 Playwright 의 Chromium 을 쓴다(`chromium.launch()`).

```sh
# 저장소 안에 받기(package.json 은 바뀌지 않는다. node_modules/ 는 gitignore)
npm install --no-save playwright
npx playwright install chromium
npm run test:web
# 또는 전역으로 받았으면
NODE_PATH="$(npm root -g)" node tests/web-smoke.js
```

`playwright` 를 불러오지 못하거나 브라우저를 띄우지 못하면 두 스크립트 모두 그렇게 찍고 종료 코드 0 으로 끝난다.
하나라도 실패하면 종료 코드 1 이다.

### `web-diff.js`

`public/index.html` 을 `file://` 로 열고 진짜 입력(키, 클릭, 타자)으로만 움직인다. 같은 입력을 Node 에서 따로 돌리는 같은 엔진(이 시험이 '원본'이라 부르는
기준. 2026-11-04 전에는 원본 하네스였다)에도 넣는다. 기준의 상태는 엔진의 내부 상태를 원래 컨트롤 이름으로 읽어(`stateS`) 화면 값을 따로 셈하고,
엔진의 `view()` 는 쓰지 않는다. 그래서 이 시험은 화면이 사람의 입력을 엔진에 바르게 보내는지와 엔진 상태를 바르게 그리는지를 본다
(엔진이 원본과 같은지는 `engine-golden` 이 본다). 화면이 엔진에 보낸 값을 받아 쓰지 않고, 사람이 원본에서 했을 입력을 그대로 넣는다.
화면에서 꺼진 단추를 누르거나 확인 창에서 취소하면 기준에는 아무것도 넣지 않는다. 조작마다 다음을 맞춘다.
- 캐릭터/타입, LV, POINT, 일곱 스탯의 값·필요 포인트·비용이 오르는 값('N부터 M', 초록 숫자 N이 상한 이상이면 '상한 N'), HP/MP/SP 값과 범위, 보너스 칸과 보너스 기록, 단추가 켜져 있는지,
  주력 계열의 선택과 고를 수 있는 줄, ▲ 표시와 '직전 조작', 로그 표의 줄, 화면에 NaN/undefined 가 없는지, 콘솔
- '복사'가 클립보드에 넣는 글(재분배 로그, 육성 가이드) = 기준의 `logOut()`/`recipe()` 글(줄바꿈 `\r\n`)
- 대시 단추의 'N까지'와 '다음 레벨업'을 기준 사본(처음부터 다시 돌린 것)에서 실제로 해 본 결과와, POINT 밑 한 줄('STAB 3회(12) 찍으면 2 남음' 등)을 기준 사본에서
  +1 을 그만큼 눌러 본 결과와
- 확인 창의 글(타입 이름을 알아보지 못하거나 상한에 맞춰 읽을 때의 말 포함), 로그 불러오기 뒤의 안내와 그 색조(첫 타입으로 읽었다는 말과 고치는 법
  문장, 상한에 맞춰 읽었다는 말), 붙여넣은 로그 칸을 비우는지(캐릭터/타입 줄의 캐릭터와 타입을 알아보고 오류 없이 읽었을 때만 비운다), 보이는 육성 가이드 패널

너비 셋(1440 × 900, 1024 × 768, 390 × 844)을 돌아가며 쓴다. 무작위 조작 전에 정해 둔 순서 24개를 돈다. 19가지(로아미니, 최고 레벨 LV 255,
스탯 상한 255, 스탯 편집, 편집을 넘는 되돌리기, 불러오기 뒤 되돌리기, 일본어판 로그, 중간에 멈추는 불러오기, 처음까지 되돌린 계획, 설정 줄만 있는 글,
스탯 편집 빈 칸, 상한에서 시작하는 비용 단계, 옛 판의 타입 이름을 적은 로그(첫 타입으로 읽고 글을 남긴 뒤 고쳐서 다시 불러오기), 상한이 285이던 판의
스탯 편집 로그(`Status` LV 270, STAB 280: 상한으로 읽고 알리기. 옛 타입 이름으로 한 번, 지금 이름으로 한 번), LV 285 까지 간 옛 로그(최고 레벨에서
멈추고 알리기. 캐릭터/타입 줄을 지운 같은 로그도), LV 256 전에 스탯이 상한을 넘은 옛 몰빵 로그(상한을 넘는 값이 `LV:` 요약 줄에만 있다: 상한에 맞춰
읽었다고 알리기) 등)를 넓은 너비에서 한 번씩 돌고, 그중 5가지(스탯 편집 LV 1, 스탯 편집 직후, 중간에 멈추는 불러오기, 처음까지 되돌린 계획,
상한을 넘는 옛 스탯 편집 로그)는 휴대폰 너비에서 한 번 더 돈다. 새 순서는 목록 끝에 더해 앞 순서들의 seed 가 그대로다.
좁은 너비(1024, 390)에서는 로그 불러오기 뒤 화면이 안내가 보이게 스크롤하므로(부드럽게, 250ms 뒤 한 번 더) 스크롤이 멈출 때까지 기다린 뒤 다음 조작을 한다
(멈추기 전에 누를 자리를 셈하면 다른 줄을 누른다. 2026-11-04 에 그것으로 한 번 어긋나 더했다).
어긋나면 seed, 몇 번째 조작인지, 조작 목록, 다른 칸을 찍고 그 seed 를 멈춘다. 끝에 'refused-but-changed'(원본처럼 중간에 멈춘 불러오기 뒤에
거절된 ←/→/대시가 비용 숫자를 바로잡은 횟수)를 세어 찍는다. 차이가 아니다.

| 환경 변수 | 뜻 |
|---|---|
| `WEBDIFF_PROBE=n` | n 조작마다 일곱 대시와 다음 레벨업을 기준 사본에서 실제로 해 본다(기본 5, 0 이면 끈다) |
| `WEBDIFF_SCRIPTS=0` / `only` / `only:글자` | 정해 둔 순서를 건너뛴다 / 그것만 돌린다 / 이름에 그 글자가 든 것만 돌린다 |
| `WEBDIFF_EMPTY=1` | 스탯 편집에서 칸을 비우는 입력도 넣는다(화면도 원본 Flex 처럼 빈 칸을 그 칸의 최솟값으로 읽는다) |
| `WEBDIFF_VERBOSE=1` | 조작을 하나씩 찍는다 |
| `WEBDIFF_SHOTS=폴더` | 어긋난 곳의 화면을 그 폴더에 남긴다 |
| `WEBDIFF_WEB=폴더` | `public/` 대신 그 폴더의 `index.html` 을 연다(일부러 고장 낸 화면을 이 시험이 잡아내는지 볼 때) |
| `WEBDIFF_TRACE=폴더` | 어긋나면 화면 조작과 기준에 넣은 조작(JSON)을 그 폴더에 남긴다 |
| `ORESIM_ENGINE=경로` | 기준 엔진으로 그 파일을 쓴다(화면은 `public/` 의 엔진 그대로) |

이 시험이 실제로 어긋남을 잡는지는 `app.js` 를 일부러 고장 낸 사본(`WEBDIFF_WEB`)으로 확인했다. 원본 하네스가 기준이던 때 24가지(대시 이름표를
초록 숫자에서 읽기, 복사 줄바꿈 `\n`, 보너스 칸에 친 값을 그대로 보이기, 로그 보기에 `logPane()` 쓰기, 스탯 편집으로 시작한 계획을 지울 때 묻지 않기 등)와
2026-11-03 의 5가지(확인 창·불러온 뒤 안내에서 상한 문장 빼기, 안내 색조를 ok 로, 고치는 법 문장 빼기, 상한에 맞춰 읽은 뒤 칸을 남기기)를 모두 잡았고,
기준을 Node 엔진으로 바꾼 2026-11-04 에도 3가지(복사 줄바꿈 `\n`, `I` 키가 DEF 를 올리게, 상한에서 시작하는 단계의 '상한 255' 빼기)를 모두 잡았다.

## 엔진의 반복 안전장치

원본에는 Flash 의 스크립트 시간 제한(Flex 기본 60초, Error #1502)밖에 없고, 그 시점은 PC 속도에 따라 달라 흉내 낼 수 없다.
엔진은 "원본이 시간 제한 없이 끝까지 돌았을 때"의 결과를 내고, 끝까지 돌아도 결과가 같은 반복만 정확하게 건너뛴다.
- 로그 읽기의 레벨 반복(`LV n - m`, 몰빵): 최고 레벨에서 한 바퀴 동안 아무것도 바뀌지 않으면 남은 바퀴도 모두 같다.
- `STAB * n`: 같은 스탯이 이어지는 칸에서 한 번 거절되면 상태가 그대로이므로 나머지도 모두 거절된다(칸을 늘어놓지 않는다).
- 되돌리기의 `stLog` 복사: 값이 있는 칸만 옮긴다(2026-11-03 부터 `Status` 줄의 LV 는 상한으로 읽으므로 로그로는 LV 가 아주 커지지 않는다.
  손으로 고친 저장 상태 같은 것에 대한 대비로 둔다).

그래도 끝이 없는 입력(`Status` 줄의 아주 작은 LV·스탯 값 때문에 레벨업·투자가 실제로 수억 번 일어나는 것)만 한 조작에서
실제 레벨업·스탯 +1 이 10만 번(기록 10만 개, 메모리 보호) 또는 반복이 1000만 번을 넘으면 멈춘다. 그때 그 조작은 `error: true` 로
끝나고 상태는 거기까지 바뀐 채로 남는다. 정상 사용은 한 조작에 많아야 2천 번 남짓이다.

## 엔진이 따르는 AS3/Flex 의미

엔진은 원본 AS3 를 JS 로 옮겼다. JS 로 돌리면 AS3/Flex 와 달라지는 곳은 아래처럼 맞췄다(원본 하네스도 같은 의미로 원본을 돌렸다).

- **C1 NumericStepper**: 코드로 넣은 값은 다음 프레임 `commitProperties` 에서야 `stepSize` 로 반올림·클램프된다.
  그 전(같은 핸들러 안)에 읽으면 넣은 값 그대로다. 예를 들어 붙여 넣은 로그의 `Bonus : 33%` 는 같은 읽기 안의 레벨업에는 33 으로,
  그 뒤에는 35 로 쓰인다. 사용자가 입력란에 친 값은 바로 검사해 확정하고 숫자가 아니면 무시한다.
- **C2 ComboBox**: `selectedIndex` 는 int 이고 목록 길이를 넘으면 마지막 항목으로 줄인다. `selectedItem` 은 저장값이다.
  목록이 비면 -1, 첫 항목이 들어오면 0. `styleList` 를 새로 만들면 데이터 바인딩으로 목록이 바뀐다.
  `change` 는 고른 번호가 바뀔 때만 난다(같은 캐릭터를 다시 골라도 초기화되지 않는다).
- **C3 ArrayCollection**: `getItemAt` 범위 밖은 RangeError, `removeAll`/`addItem` 은 RESET/ADD 이벤트.
- **C4 Text/Label/TextArea**: `text` 에 null·undefined·"" 를 넣으면 "".
- **C5 RegExp `\s`**: AS3(avmplus 의 PCRE)는 `\t \n \f \r` 공백, U+00A0, U+200B, U+2060, U+3000, U+FEFF 만 맞춘다
  (`\v`, U+1680, U+2000~U+200A, U+2028, U+2029, U+202F, U+205F 는 맞추지 않는다). Xien 줄 다듬기가 이 집합을 쓴다.
- **C6 타입 있는 변수**: `var x:Number;`·`= undefined` 는 NaN, String 형 변수·매개변수에 넣는 값은 String(undefined → null),
  Number 형 변수·전역에 배열 값을 넣을 때는 Number 로 바꾼다.
- **C7 `(x as Text)`**: Text 가 아니면 null 이 되어 `.text` 에서 TypeError.
- **C8 처리되지 않은 예외**: Flash 처럼 그 핸들러만 멈추고 거기까지 바뀐 상태는 남는다.
- **C9 `callLater`**: 바로 실행한다(스크롤 위치만 바꾼다).
- **C10 전역 `parseInt`**: AS3 의 것(avmplus `MathUtils::parseInt`, radix 0)으로 바꾼다. 앞 공백은 `' ' \t \n \v \f \r`,
  U+2000~U+200B, U+2028, U+2029, U+205F, U+3000 만 건너뛰고(JS 와 달리 U+00A0·U+FEFF·U+1680·U+202F 는 건너뛰지 않는다),
  수는 자릿수마다 `result * radix + v` 로 쌓는다(10진수는 17자리쯤부터 JS 와 값이 다르다. 16진수는 2^53 이상에서 반올림 보정).

C1~C4 는 Apache Flex SDK 4.16.1 의 mx 소스, C5·C10 은 avmplus(Tamarin) 소스(`pcre_chartables.cpp`, `pcre_exec.cpp`,
`pcre_config.cpp`, `MathUtils.cpp`, `Toplevel.cpp`)를 읽고 맞췄다. Flash Player 로 직접 확인하지는 못했다.
C5·C10 은 `as3-semantics.js` 가 답과 참고 구현으로 본다.

엔진의 계약 해석: 상태를 바꿀 수 있는 조작은 모두 `{ ok, sound }` 를 돌려주고(받아들이지 않은 조작은 소리 없음, 최고 레벨에서 포인트가 모자라
아무것도 못 하는 대시도 `ok: false`), `importLog` 는 `footer`/`typeFound`/`restarted`/`capped` 를 더 돌려준다. `capped`(읽은 글에 지금 상한을 넘는 값이
있었다)는 원본에 없는 값이다. 원본 하네스는 엔진 코드를 쓰지 않고 원본 `logLoad` 의 글 다루기를 따로 옮긴 `overCapText()` 로 같은 값을 정해 맞춰
보았다(그 결과가 정답 기록에 들어 있다). `exportLog()`/`guide()` 는 글만 만들고 로그 상자는 그대로 두며, `logPane()` 은 원본의 로그 상자 글이다.

`fixtures/ja-era-logs.js` 는 한국어화 직전 일본어판(커밋 `14906f3`)이 출력한 로그다. 저장소에 일본어 문자를 남기지 않으려고
ASCII 밖의 글자는 `\u` 이스케이프로 적었다.
