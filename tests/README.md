# tests — 웹판 검증

웹판 계산 엔진(`web/js/engine.js`)이 원본 Flash 판(`oresim/oresim-main.as`)과 **동작이 같은지**, 그리고 화면(`web/`)이 엔진·원본과
같은 것을 보여 주는지 확인하는 스크립트들이다. 저장소 맨 위에서 실행한다.
엔진 시험 넷은 Node 22 만 있으면 된다(npm 설치 없음). 화면 시험 둘(`web-smoke.js`, `web-diff.js`)은 선택이다: Playwright 가 있을 때만 돌고,
없으면 그렇게 말하고 종료 코드 0 으로 끝난다(아래 '화면 시험').

| 스크립트 | 확인하는 것 |
|---|---|
| `node tests/const-check.js` | `web/js/const.js` 가 `oresim/oresim-const.as` 의 표와 깊이 같은지, `tools/gen-web-const.js` 로 다시 만든 결과와 바이트 단위로 같은지(손으로 고치지 않았는지), 표가 얼어 있는지, 엔진의 스테퍼 한계와 스테퍼 표(`STEPPER_DEFS`), `oresim_offline.mxml` 의 스테퍼가 `oresim.mxml` 과 같은지, 로그 읽기가 기대는 데이터 성질(이름 규칙, 기본 계열 등), 두 파일을 UTF-8 이 아닌 문자 코드(latin1, windows-1252, EUC-KR, Shift_JIS)로 읽어도 표와 출력이 같은지 |
| `node tests/as3-semantics.js [개수=40000] [seed=1]` | 엔진과 하네스가 흉내 내는 AS3 의 전역 `parseInt` 와 RegExp `\s` 가 avmplus 소스에서 따진 답과 같은지, 무작위 글자열에서 두 구현이 서로 같은지 |

| `node tests/web-smoke.js` | **화면 연기 시험(선택, Playwright).** 시작, 진짜 키·클릭 뒤 화면의 숫자 = `OresimUI.engine().view()`, 새로 고침 뒤 되살리기, 공유 링크 왕복, 붙여넣은 로그 왕복, 앞 판의 자동 저장, 이름이 바뀐 타입과 상한을 넘는 옛 계획의 알림, LV 범위 줄이 있는 1440 × 900 페이지 높이, 깨끗한 콘솔 등 22가지(아래) |

걸리는 시간(이 작업 환경에서 잰 값): `gen-web-const --check`·`const-check`·`as3-semantics` 각 1초 안, `engine-diff` 기본값 약 100초
(`300 400` 약 8분, `8 1500 1001` 약 50초), `engine-invariants` 약 55초, `web-smoke` 약 25초, `web-diff` 정해 둔 순서만(`WEBDIFF_SCRIPTS=only`)
약 2분 40초, `web-diff 2 60` 약 2분 20초(`10 120` 약 7분. 둘 다 정해 둔 순서가 20개이던 때).
기계가 바쁜 정도에 따라 크게 달라진다: 2026-11-03에 다른 일 없이 차례로 돌렸을 때 `engine-diff 20 400` 약 73초, `engine-diff 4 1500 1001` 약 58초,
`engine-invariants` 약 66초였다(2026-11-02에는 `engine-diff 8 1500 1001` 약 82초).

완료 기준으로 돌린 명령:

```sh
node tools/gen-web-const.js --check   # const.js 가 최신인지
node tests/const-check.js
node tests/as3-semantics.js
node tests/engine-diff.js 300 400     # 어긋남 0
node tests/engine-diff.js 8 1500 1001 # 긴 seed: 최고 레벨(255)과 스탯 상한(255)까지 간다
node tests/engine-invariants.js
node tests/web-smoke.js               # ALL PASS (Playwright 가 있을 때)
node tests/web-diff.js 10 120         # 어긋남 0 (Playwright 가 있을 때)
```

최고 레벨과 스탯 상한은 스크립트마다 표(`MAX_LEVEL`, `MAX_STATUS`)에서 읽는다(지금 둘 다 255). 상한 둘레의 값(MAX−1, MAX, MAX+1), 무작위 값의 범위(1~MAX),
정해 둔 순서의 이름에 든 숫자('LV 255 까지', '스탯 상한 255')도 그것으로 만들므로, 상한만 바꿀 때는 시험을 고치지 않는다.
일부러 범위 밖으로 넣는 값(300, 999, 160000 등)은 상한이 255 여도 범위 밖이다.
상한이 285이던 판의 계획처럼 상한을 넘는 값(상한 + 1, 상한 + 15, 상한 + 30 등)도 표의 상한에서 셈한다.

`engine-invariants.js` 는 상한이 285이던 판의 로그를 따로 확인한다(`special` 의 `capped.*`, 2026-11-03).
- `capped.edit78`, `capped.edit46`: 옛 스탯 편집 로그(`Status` LV 최고 레벨 + 15, STAB 상한 + 25, DEX 상한 + 15, 78칸·46칸)를 상한으로 읽어 정해 둔 값
  (LV·시작 LV 255, 스탯, 최고 레벨에서 찍은 AGI 두 번의 필요 포인트만큼 준 POINT, 다시 내보낸 `Status` 칸)이 되고, 다시 내보낸 로그는 `capped` 없이
  같은 계획·같은 글인지
- `capped.levelRange`: 최고 레벨을 넘는 LV 범위(`LV 2 - 285 : STAB`)가 최고 레벨에서 멈추고, `LV 2 - 255 : STAB` 에 `LV 255 : STAB * 30` 을 더한 글과
  같은 계획인지
- `capped.atCap`: 상한 그대로는 `capped` 가 아니고 값도 그대로이며, 한 칸(LV 또는 스탯 하나)만 상한 + 1 이면 `capped` 이고 그 칸만 상한으로 읽는지
- `capped.otherFields`: HP/MP/SP 와 그 범위, POINT 는 상한을 넘어도 그대로 읽고(`capped` 도 아니다) 기록 `log[0]` 에 그대로 남는지
- `capped.afterError`: 읽기가 예외로 멈춰 뒤의 줄을 읽지 않아도 상한을 넘는 줄이 있으면 `capped` 가 참인지
- `capped.nanNegative`: 수가 아닌 값과 음수는 `capped` 가 아니고 바뀌지 않으며, 원본(하네스)이 읽은 결과·상태·로그와 같은지
- `capped.summaryLine`: LV 는 상한을 넘지 않았는데 스탯이 상한을 넘은 옛 몰빵 로그(상한을 넘는 값이 끝의 `LV:` 요약 줄에만 있다)가 `capped` 이고,
  요약 줄은 계획을 바꾸지 않으며(그 줄이 없는 글과 같은 계획·같은 로그 글), 다시 내보낸 로그는 `capped` 가 아닌지. 요약 줄의 여러 모양(상한 그대로,
  LV 만 상한 + 1, 스탯마다 상한 + 1, 끝에 덧붙인 말, 전각 콜론, 이름이 빠지거나 다르거나 순서가 바뀐 줄, `LV :` 머리, 수가 아닌 값·음수)에서
  엔진과 원본(하네스)의 `capped` 가 정해 둔 답과 같은지. 상한을 넘는 요약 줄이 마지막 줄이 아니어도(뒤에 빈 줄이나 덧붙인 말이 있는 글,
  캐릭터/타입 줄 앞이나 글 맨 앞에 둔 글) `capped` 이고 계획은 그대로인지
- `budget.undoHugeLv`: 아주 큰 `Status` LV(99999999)를 상한으로 읽는지 보고, 그런 상태는 이제 로그로 만들 수 없으므로 지금 엔진의
  `serialize()` 를 손으로 고쳐(LV 글자, 기록의 LV 칸, 레벨마다의 `stLog`/`tmpStLog` 키를 밀어) LV 99999999 에 조작 셋이 있는 저장 상태를 되살린 뒤,
  되돌리기·다시 실행(Shift 포함) 네 번이 모두 받아들여져 1초 안에 끝나고 처음 계획으로 돌아오는지 본다(되돌리기가 레벨 수만큼 돌면 작업 한도에서 멈춘다).
- 무작위 왕복의 FLAGS 는 내보낸 로그와 끝 두 줄을 뺀 로그가 `capped` 가 아닌지 본다.

`DIFF_VERBOSE=1` 을 주면 차등 퍼저가 조작을 하나씩 찍는다. `ORESIM_ENGINE=경로` 를 주면 그 엔진 파일로 돌린다
(일부러 고장 낸 엔진을 이 테스트들이 잡아내는지 볼 때 쓴다).

## 화면 시험(선택: Playwright)

저장소는 npm 을 쓰지 않으므로 Playwright 는 저장소 밖에 둔다. `require('playwright')` 가 되는 Node 에서 돌리면 된다.
전역으로 설치했다면 전역 모듈 폴더를 `NODE_PATH` 로 알려 준다. 브라우저는 Playwright 의 Chromium 을 쓴다(`chromium.launch()`).

```sh
# 예: 전역 설치(저장소에는 package.json 을 두지 않는다)
npm install -g playwright
npx playwright install chromium
NODE_PATH="$(npm root -g)" node tests/web-smoke.js
NODE_PATH="$(npm root -g)" node tests/web-diff.js 2 60
```

`playwright` 를 불러오지 못하거나 브라우저를 띄우지 못하면 두 스크립트 모두 그렇게 찍고 종료 코드 0 으로 끝난다.
하나라도 실패하면 종료 코드 1 이다.

### `web-smoke.js`

`web/` 을 작은 http 서버(127.0.0.1, 빈 포트)로 내보내고 Chromium 으로 연다. 22가지를 확인한다.
- 새 계획으로 시작하고 `window.OresimUI` 가 `render, dispatch, playSound, shareLink, engine` 인지
- 진짜 키(L L L S S Shift+A ← →)와 클릭(레벨업, HACK +1, STAB 대시) 뒤 화면의 POINT, LV, HP/MP/SP, 스탯 값과 필요 포인트,
  대시 단추의 'N까지'(`previewDash`), 로그 표의 글(`exportLog()`)이 엔진과 같은지
- 보너스 칸에 62 를 치면 엔진이 60 으로 확정하고 칸도 60 인지
- 새로 고침 뒤 자동 저장에서 같은 계획(`view()`, 로그)과 되돌리기 기록이 되살아나는지
- 링크 복사가 계획 전체(`{ v, log, b, x }`)를 담고, 그 링크를 새 브라우저(390 × 844)에서 열면 같은 계획이 되고 주소의 `#` 가 지워지는지
- 지울 계획이 있는 탭에 다른 계획의 링크가 오면 묻고, 묻는 동안 링크가 주소창에 남아 새로 고쳐도 다시 묻고, '저장된 계획 유지'가 계획을 두고 링크를 지우는지
- 손으로 만든 링크(`Status` 줄 둘, LV -99999 인 `Status` 줄)를 1.5초 안에 거절하고 계획이 그대로인지
- 붙여넣은 로그를 불러오면 같은 계획이 되는지
- 앞 판(`ENGINE_VERSION` 이 다른 엔진)의 자동 저장: 엔진 상태로는 되살리지 못하니 저장된 로그에서 다시 만들어 알리고(새 엔진의 `importLog` +
  `setBonus` + `setXien` 과 같은 계획) 곧 지금 판으로 다시 저장하는지
- 2026-11 에 이름이 바뀐 타입(`루시안/베기`)을 적은 앞 판의 자동 저장: 첫 타입으로 읽었다고도 알리고, 새로 고쳐도 다시 알리며, 계획을 바꿀 때까지
  옛 기록을 덮어쓰지 않는지(바꾸면 지금 판으로 저장한다). 같은 로그를 담은 공유 링크가 연 뒤에 '링크의 계획을 열었습니다. 타입 이름을 알아보지 못해
  첫 타입(물리복합)으로 읽었습니다.'라고 알리는지
- 상한이 285이던 판에서 스탯 편집으로 만든 계획(그 판의 로그 모양: `Status` 줄의 LV 최고 레벨 + 15, STAB 상한 + 25, DEX 상한 + 15, 최고 레벨 + 30 까지):
  그 공유 링크가 새 브라우저에서 묻지 않고 상한으로 열리고(LV 255, 스탯 255 이하, 주소의 `#` 는 지운다) 'LV나 스탯이 상한(255)을 넘어 상한에 맞춰
  읽었습니다.'라고 알리는지, 앞 판의 자동 저장이 상한으로 다시 만들어져 그렇게 알리고 곧 `ENGINE_VERSION` '3' 과 `Status` LV 255 로 다시 저장되는지
- 1440 × 900 에서 LV 범위 줄이 있는 계획의 로그 탭과 가이드 탭 모두 문서 높이가 900 그대로인지(로그 표·가이드 안 화면 낭독기용 글이 그 칸을 기준으로 자리 잡는다)
- 콘솔에 오류·경고가 없는지

공유 링크 왕복에서 알려진 예외 하나: 조작 0회인 계획(처음까지 되돌린 계획 등)의 로그 첫머리 `Bonus` 줄은 원본이 기록 맨 앞 칸에 덧쓴 값이라
받는 쪽에서 같은 글로 다시 만들 수 없다(원본도 같다). 보너스 값은 링크의 `b` 로 같아진다(`web/js/app.js` 의 `linkCandidate`).

### `web-diff.js`

`web/index.html` 을 `file://` 로 열고 진짜 입력(키, 클릭, 타자)으로만 움직인다. 같은 입력을 원본(`harness.js` 의 `createOracle()`)에도 넣는다.
화면이 엔진에 보낸 값을 받아 쓰지 않고, 사람이 원본에서 했을 입력을 그대로 넣는다. 화면에서 꺼진 단추를 누르거나 확인 창에서 취소하면 원본에는
아무것도 넣지 않는다. 조작마다 다음을 맞춘다.
- 캐릭터/타입, LV, POINT, 일곱 스탯의 값·필요 포인트·비용이 오르는 값('N부터 M', 초록 숫자 N이 상한 이상이면 '상한 N'), HP/MP/SP 값과 범위, 보너스 칸과 보너스 기록, 단추가 켜져 있는지,
  주력 계열의 선택과 고를 수 있는 줄, ▲ 표시와 '직전 조작', 로그 표의 줄, 화면에 NaN/undefined 가 없는지, 콘솔
- '복사'가 클립보드에 넣는 글(재분배 로그, 육성 가이드) = 원본의 `logOut()`/`recipe()` 글(줄바꿈 `\r\n`)
- 대시 단추의 'N까지'와 '다음 레벨업'을 원본 사본에서 실제로 해 본 결과와, POINT 밑 한 줄('STAB 3회(12) 찍으면 2 남음' 등)을 원본 사본에서
  +1 을 그만큼 눌러 본 결과와
- 확인 창의 글(타입 이름을 알아보지 못하거나 상한에 맞춰 읽을 때의 말 포함), 로그 불러오기 뒤의 안내와 그 색조(첫 타입으로 읽었다는 말과 고치는 법
  문장, 상한에 맞춰 읽었다는 말), 붙여넣은 로그 칸을 비우는지(캐릭터/타입 줄의 캐릭터와 타입을 알아보고 오류 없이 읽었을 때만 비운다), 보이는 육성 가이드 패널

  이제 무겁지 않지만 그 뒤 조작이 원본과 같은지 그대로 본다.

## 엔진의 반복 안전장치

원본에는 Flash 의 스크립트 시간 제한(Flex 기본 60초, Error #1502)밖에 없고, 그 시점은 PC 속도에 따라 달라 흉내 낼 수 없다.
엔진은 "원본이 시간 제한 없이 끝까지 돌았을 때"의 결과를 내고, 끝까지 돌아도 결과가 같은 반복만 정확하게 건너뛴다.
- 로그 읽기의 레벨 반복(`LV n - m`, 몰빵): 최고 레벨에서 한 바퀴 동안 아무것도 바뀌지 않으면 남은 바퀴도 모두 같다.
- `STAB * n`: 같은 스탯이 이어지는 칸에서 한 번 거절되면 상태가 그대로이므로 나머지도 모두 거절된다(칸을 늘어놓지 않는다).
- 되돌리기의 `stLog` 복사: 값이 있는 칸만 옮긴다(2026-11-03 부터 `Status` 줄의 LV 는 상한으로 읽으므로 로그로는 LV 가 아주 커지지 않는다.
  손으로 고친 저장 상태 같은 것에 대한 대비로 둔다).

그래도 끝이 없는 입력(`Status` 줄의 아주 작은 LV·스탯 값 때문에 레벨업·투자가 실제로 수억 번 일어나는 것)만 한 조작에서
실제 레벨업·스탯 +1 이 10만 번(기록 10만 개, 메모리 보호) 또는 반복이 1000만 번을 넘으면 멈춘다. 그때 그 조작은 `error: true` 로
끝나고 상태는 거기까지 바뀐 채로 남는다. 정상 사용은 한 조작에 많아야 2천 번 남짓이다.

## 하네스(`harness.js`)

원본 AS3 를 Node `vm` 에서 그대로 돌리는 기준(oracle)이다. 원본 로직은 고치지 않고 AS3 전용 문법(타입 표기 등)만 지운다.
원본은 저장소의 지금 `oresim/oresim-main.as` 다(2026-11-03 에 상한을 넘는 `Status` 줄의 LV·스탯을 상한으로 읽게 고쳤다).
JS 로 돌리면 AS3/Flex 와 달라지는 곳은 아래처럼 맞췄고, 엔진도 같은 의미를 따른다. 보정은 적용 횟수를 확인하므로
원본이 바뀌어 보정이 빠지면 바로 실패한다.

- **C1 NumericStepper**: 코드로 넣은 값은 다음 프레임 `commitProperties` 에서야 `stepSize` 로 반올림·클램프된다.
  그 전(같은 핸들러 안)에 읽으면 넣은 값 그대로다. 예를 들어 붙여 넣은 로그의 `Bonus : 33%` 는 같은 읽기 안의 레벨업에는 33 으로,
  그 뒤에는 35 로 쓰인다. 사용자가 입력란에 친 값은 바로 검사해 확정하고 숫자가 아니면 무시한다.
- **C2 ComboBox**: `selectedIndex` 는 int 이고 목록 길이를 넘으면 마지막 항목으로 줄인다. `selectedItem` 은 저장값이다.
  목록이 비면 -1, 첫 항목이 들어오면 0. `styleList` 를 새로 만들면 데이터 바인딩으로 목록이 바뀐다.
  `change` 는 고른 번호가 바뀔 때만 난다(같은 캐릭터를 다시 골라도 초기화되지 않는다).
- **C3 ArrayCollection**: `getItemAt` 범위 밖은 RangeError, `removeAll`/`addItem` 은 RESET/ADD 이벤트.
- **C4 Text/Label/TextArea**: `text` 에 null·undefined·"" 를 넣으면 "".
- **C5 RegExp `\s`**: AS3(avmplus 의 PCRE)는 `\t \n \f \r` 공백, U+00A0, U+200B, U+2060, U+3000, U+FEFF 만 맞춘다
  (`\v`, U+1680, U+2000~U+200A, U+2028, U+2029, U+202F, U+205F 는 맞추지 않는다). Xien 줄 다듬기가 이 집합을 쓴다.
- **C6 타입 있는 변수**: `var x:Number;`·`= undefined` 는 NaN, String 형 변수·매개변수에 넣는 값은 String(undefined → null),
  Number 형 변수·전역에 배열 값을 넣을 때는 Number 로 바꾼다.
- **C7 `(x as Text)`**: Text 가 아니면 null 이 되어 `.text` 에서 TypeError.
- **C8 처리되지 않은 예외**: Flash 처럼 그 핸들러만 멈추고 거기까지 바뀐 상태는 남는다.
- **C9 `callLater`**: 바로 실행한다(스크롤 위치만 바꾼다).
- **C10 전역 `parseInt`**: AS3 의 것(avmplus `MathUtils::parseInt`, radix 0)으로 바꾼다. 앞 공백은 `' ' \t \n \v \f \r`,
  U+2000~U+200B, U+2028, U+2029, U+205F, U+3000 만 건너뛰고(JS 와 달리 U+00A0·U+FEFF·U+1680·U+202F 는 건너뛰지 않는다),
  수는 자릿수마다 `result * radix + v` 로 쌓는다(10진수는 17자리쯤부터 JS 와 값이 다르다. 16진수는 2^53 이상에서 반올림 보정).

C1~C4 는 Apache Flex SDK 4.16.1 의 mx 소스, C5·C10 은 avmplus(Tamarin) 소스(`pcre_chartables.cpp`, `pcre_exec.cpp`,
`pcre_config.cpp`, `MathUtils.cpp`, `Toplevel.cpp`)를 읽고 맞췄다. Flash Player 로 직접 확인하지는 못했다.

어댑터(`createOracle`)는 엔진과 같은 계약 해석을 쓴다: 상태를 바꿀 수 있는 조작은 모두 `{ ok, sound }` 를 돌려주고

`footer`/`typeFound`/`restarted`/`capped` 를 더 돌려준다. `capped`(읽은 글에 지금 상한을 넘는 값이 있었다)는 원본에 없는 값이라 엔진 코드를 쓰지
